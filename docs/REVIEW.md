# PrivateVault 설계 가능성 및 보안 검토 (v1)

- 대상: [docs/PRD.md](PRD.md) v1.0 + Owner 추가 요구사항 (2026-10-30)
- 작성: Claude Code (기획·검토 단계, 코드 변경 없음)
- 결론: **설계 가능.** 단, "3회 오류 시 영구 잠금"은 *정상(탈옥·루팅되지 않은) 기기*에서 확실히 지킬 수 있고, 탈옥·루팅·포렌식 장비를 쓰는 공격자에게는 완벽하게 보장할 수 없습니다. 아래에 이유와 대응을 정리했습니다.

## 1. Owner 추가 요구사항

| # | 요구사항 | 가능 여부 | 핵심 조건 |
|---|---|---|---|
| R1 | 비밀번호는 패턴 또는 숫자 PIN만 사용 | 가능 | 짧은 비밀번호의 약점은 **하드웨어 키 결합 + 3회 제한**으로 보완 |
| R2 | 기능은 보관·열람만 | 가능 | 공유·내보내기 코드 자체를 만들지 않음 (가장 안전한 방식) |
| R3 | 비밀번호 3회 틀리면 영구 접속 불가 | 가능 (조건부) | 3번째 실패 시 **암호화 키를 파기** (Cryptographic Erasure, 키를 지워서 데이터를 영원히 못 읽게 만드는 방식) |
| R4 | 재설치해도 기존 파일 접속 불가 | 가능 | iOS는 앱을 지워도 Keychain(시스템 비밀 저장소)이 남으므로 **첫 실행 시 잔존 키 강제 삭제** 필요 |
| R5 | 사진첩에서 사진 선택 → 금고로 이동 | 가능 | "이동" = 암호화 저장 + 검증 후 OS에 원본 삭제 요청. 삭제는 OS가 사용자에게 한 번 더 확인 창을 띄움 |

### R1. 짧은 PIN·패턴의 보안 수준

짧은 비밀번호는 경우의 수가 적습니다.

| 방식 | 경우의 수 (이론값) |
|---|---|
| 숫자 4자리 | 10,000 |
| 숫자 6자리 | 1,000,000 |
| 숫자 8자리 | 100,000,000 |
| 3×3 패턴 (Android 기본형, 4~9점) | 약 389,000 (실제 사람이 고르는 패턴은 훨씬 적음) |
| 4×4 패턴 | 수십억 이상 (기억·입력 난이도 높음) |

컴퓨터는 1백만 개를 몇 초~몇 분이면 전부 시도할 수 있으므로, **PIN만으로 키를 만들면 안 됩니다** (PRD 4.2와 동일). 대신:

1. 암호화 키를 풀려면 **PIN + 휴대폰 보안칩 안의 키**가 둘 다 필요하게 만듭니다. 보안칩 키는 휴대폰 밖으로 꺼낼 수 없으므로, 데이터 파일을 복사해 PC에서 무한 대입하는 공격이 막힙니다.
2. 휴대폰 위에서 시도할 수 있는 횟수는 **3회**로 제한합니다. 무작위 6자리 PIN이라면 3번 안에 맞힐 확률은 약 0.0003%입니다.
3. 사람들이 자주 쓰는 PIN(123456, 000000, 생일 형태 등)과 단순 패턴(ㄱ자, 일자)은 **등록 단계에서 차단**합니다. 3회 제한에서는 "흔한 비밀번호 상위 3개"가 실제 위협이기 때문입니다.

**권고:** 숫자 PIN 최소 6자리(권장 8자리), 패턴은 최소 6점 이상 + 단순 패턴 차단.

### R3. 3회 오류 = 영구 잠금 — 어떻게, 어디까지

**설계:**
- 시도 횟수는 비밀번호를 *검사하기 전에* 먼저 1 증가시켜 저장합니다. (검사 도중 앱을 강제 종료해 횟수를 피하는 공격 방지)
- 맞으면 0으로 초기화, 3에 도달하면 즉시 보안칩 키와 보호된 마스터키를 삭제합니다. 이후에는 올바른 PIN을 넣어도 열 수 없습니다.
- 잠금 화면에 "남은 시도 횟수"를 항상 표시합니다.

**한계 (정직하게 표기해야 할 부분):**
- iOS Secure Enclave와 Android Keystore는 *앱이 정한 PIN 시도 횟수*를 칩 안에서 직접 세어 주는 기능을 일반 앱에 제공하지 않습니다. (휴대폰 잠금화면용 횟수 제한은 OS 전용입니다.) 따라서 횟수 카운터는 앱이 관리합니다.
- 정상 기기에서는 앱 데이터를 몰래 복사·되돌릴 방법이 없으므로 3회 제한이 지켜집니다.
- 탈옥·루팅된 기기나 포렌식 장비로 **저장소를 통째로 복사해 두었다가 되돌리면** 횟수를 다시 얻을 수 있습니다. 그래도 보안칩 키가 그 휴대폰 밖으로 나가지 않으므로 공격은 반드시 *그 휴대폰 위에서*, 느린 키 유도(Argon2id) 비용을 치르며 해야 합니다.
- Android 12+ StrongBox의 "키 사용 횟수 제한" 기능 등 하드웨어 보강 방법은 Phase 1 PoC에서 실제 기기로 검증합니다.

**사용자 위험 (중요):** 3회 제한은 공격자뿐 아니라 **본인 실수·아이의 장난·주머니 속 오입력**에도 똑같이 발동합니다. 3번 틀리면 모든 파일이 영구 삭제됩니다. 대응:
- 지정 자릿수를 모두 입력한 경우만 1회로 계산 (패턴은 최소 점 수 미만이면 계산하지 않음)
- 2회 실패 후 "마지막 기회" 경고 화면 + 확인 버튼
- 설치 시 이 정책을 명확히 동의받음

> 참고: PRD 11장은 "기본 모드에서는 자동 삭제 없음"이었으나, 이번 Owner 요구사항(3회 → 영구 잠금)이 이를 대체합니다. SPEC.md에 Owner 결정으로 반영했습니다.

### R4. 재설치 후 기존 파일 접근 차단

- **Android:** 앱 삭제 시 앱 데이터와 Keystore 키가 함께 삭제됩니다. 자동 백업(Auto Backup)과 기기 이전을 끄면 충분합니다.
- **iOS:** 앱을 삭제해도 금고 파일은 지워지지만 **Keychain 항목은 남을 수 있습니다.** 첫 실행(설치 표시 플래그 없음)에서 남아 있는 Keychain 항목을 모두 삭제하고 새 금고를 만듭니다. 모든 키는 `ThisDeviceOnly`(이 기기 전용, 백업 불가) 등급으로 저장합니다.

### R5. 사진 선택 → 금고로 이동

1. OS 사진 선택기로 사진 선택 (iOS PHPicker / Android Photo Picker)
2. 앱 내부에서 메모리상 암호화 → 저장 → 복호화 검증
3. 검증 성공한 사진만 원본 삭제 요청
   - iOS: `PHAssetChangeRequest.deleteAssets` → 시스템 확인창 → **'최근 삭제된 항목'에 30일간 남음**
   - Android 11+: `MediaStore.createDeleteRequest` → 시스템 확인창 (기기에 따라 휴지통 경유)
4. 결과 화면에서 "저장 성공 / 원본 삭제 성공·실패"를 구분 표시하고, '최근 삭제된 항목'과 클라우드 사진(iCloud·Google Photos) 사본은 사용자가 직접 지워야 한다고 안내

앱이 원본을 사용자 확인 없이 조용히 지우는 것은 두 OS 모두 허용하지 않습니다.

## 2. 권장 키 구조 (요약)

```
마스터키 MK (무작위 256bit, 금고 생성 시 1회)
  └─ 파일별 키 FK (무작위) ──AES-256-GCM──> 암호화 파일·썸네일·메타데이터
MK 보호 키 = HKDF( Argon2id(PIN, salt), 보안칩 키로 만든 값 )
  - Argon2id: PIN 1회 검사에 의도적으로 시간이 걸리게 하는 함수
  - 보안칩 키: iOS Secure Enclave / Android StrongBox(없으면 TEE)
3회 실패 → 보안칩 키 + 보호된 MK 삭제 → 영구 접근 불가
```

## 3. PRD에서 발견한 위험·공백

| # | 항목 | 심각도 | 권고 |
|---|---|---|---|
| G1 | 3회 영구 잠금 시 실수로 전체 데이터 손실 | 매우 높음 | 남은 횟수 표시, 마지막 기회 경고, 최소 길이 미만 입력은 미계산 |
| G2 | 앱 카운터는 탈옥·루팅 + 저장소 복원으로 우회 가능 | 높음 | 루팅·탈옥 감지 시 금고 사용 차단, 하드웨어 사용 횟수 제한 PoC |
| G3 | iOS Keychain이 앱 삭제 후 남음 | 높음 | 첫 실행 시 잔존 항목 삭제 (R4) |
| G4 | 사진 원본이 '최근 삭제된 항목'·클라우드에 남음 | 높음 | 결과 화면에서 수동 정리 안내 (앱이 대신 지울 수 없음) |
| G5 | 동영상 재생 시 OS 플레이어가 평문 캐시를 만들 수 있음 | 높음 | 커스텀 데이터 소스로 청크 복호화 스트리밍 (AVAssetResourceLoader / ExoPlayer DataSource) |
| G6 | 키보드·스크린샷·앱 전환 미리보기 유출 | 중간 | 숫자 PIN은 자체 키패드 사용, Android `FLAG_SECURE`, iOS 백그라운드 가림 화면 |
| G7 | 앱 업데이트 시 금고 형식 변경으로 데이터 손상 | 매우 높음 | 금고 형식 버전 필드 + 마이그레이션 테스트 필수 |
| G8 | 휴대폰 분실·고장 = 전체 손실 (백업 없음) | 높음 | 설치 시 동의 화면에서 명확히 고지 (Owner 확정 정책) |
| G9 | "보관·열람만" 범위와 PRD의 폴더·문서·동영상 기능 범위 불일치 | 중간 | Owner 범위 결정 필요 (NEXT_STEPS 참조) |
| G10 | 크로스플랫폼(Flutter/React Native) 사용 시 보안칩 기능 접근 제약 | 중간 | 보안 핵심부는 Swift/Kotlin 네이티브로 작성 권장 |

## 4. PRD 20장 미해결 8개 항목 권고

| # | 항목 | 권고안 |
|---|---|---|
| 1 | PIN 최소 자릿수·패턴 기준 | PIN 6자리 이상(권장 8), 흔한 PIN 차단. 패턴은 3×3 최소 6점 + 단순 패턴 차단. 4×4는 선택 옵션으로 후속 검토 |
| 2 | 최소 지원 OS·기기 | iOS 16+ (Secure Enclave 있는 전 기종), Android 11+ (원본 삭제 요청 API) + 하드웨어 Keystore 필수, StrongBox 우선 |
| 3 | PIN·하드웨어 키 결합 | 2장 구조: Argon2id(PIN) + 보안칩 키 → HKDF로 결합. 어느 한쪽만으로는 복호화 불가 |
| 4 | Office 문서 열람 | MVP 제외. 사진 → 동영상 → PDF 순. Office 렌더러는 공격면이 크고 외부 라이브러리 의존 |
| 5 | 원본 삭제 UX | R5 흐름. 저장 검증 후에만 OS 삭제 요청, 결과를 성공/실패로 구분 표시 |
| 6 | 자동 자폭 조건 | Owner 결정으로 **3회 오류 = 키 파기**로 확정. 그 외 자동 파기(루팅 감지, 충돌 등)는 추가하지 않음 (오탐 위험) |
| 7 | 보안 감사 범위·예산 | MASVS L2 기준 외부 모바일 펜테스트 1회 (출시 전). 비용 발생 → 견적 후 Owner 승인 (L3) |
| 8 | 가격·출시 순서 | 일회성 유료 구매 유지. 출시 순서는 Owner 주력 기기 OS 먼저 1개 → 다른 OS (동시 개발은 보안 검증 부담 2배) |
