# 1. Executive Summary

## 1.1 제품 정의

JellyDock PrivateVault는 사용자의 사진, 동영상 및 개인문서를 휴대폰 내부에 암호화하여 저장하는 **완전 오프라인 개인 보관함**이다.

사용자가 파일을 금고에 넣으면 해당 파일은 PrivateVault 내부에서만 열람하거나 삭제할 수 있다.

**핵심 원칙**

> ONE-WAY IN. NEVER OUT. VIEW OR DESTROY.

- 금고로 가져오기만 가능
- 외부 내보내기 불가능
- 다른 사용자에게 전송 불가능
- 클라우드 보관 및 자동 백업 없음
- 계정 가입 및 서버 로그인 없음
- 비밀번호 복구 불가능
- 개발자용 마스터키 없음
- 사용자가 영구 삭제 가능

단, 운영체제가 침해되거나 다른 카메라로 화면을 촬영하는 경우까지 절대적으로 통제할 수 있다고 주장하지 않는다.

## 1.2 제품 목표

사용자가 가장 민감한 개인 파일을 별도 서비스에 맡기지 않고 자신의 휴대폰 내부에 안전하게 보관할 수 있게 한다.

### 성공 기준

1. 파일 원본이 암호화되지 않은 상태로 금고 저장소에 남지 않는다.
2. 사용자의 PIN 또는 패턴 없이는 정상적인 금고 잠금 해제가 불가능하다.
3. 개발자도 복구용 암호화 키를 보유하지 않는다.
4. 비밀번호 분실 시 기존 파일을 복구할 수 없다.
5. 금고 내부에 파일 내보내기 경로가 존재하지 않는다.
6. 서버 연결 없이 핵심 기능이 작동한다.
7. 비밀번호 분실·앱 삭제·기기 분실에 따른 데이터 손실 위험을 명확히 안내한다.

# 2. Target Users

## 주요 사용자

- 개인 사진과 영상을 비공개로 보관하려는 사용자
- 여권 사본, 계약서, 신분증 등 개인문서를 보관하는 사용자
- 클라우드 서버를 신뢰하지 않는 사용자
- 외부 공유나 동기화가 필요 없는 사용자
- 복구 편의성보다 개인정보 보호를 우선하는 사용자

## 핵심 사용자 경험

앱 실행 → 잠금 해제 → 개인 금고 → 파일 열람 또는 삭제.

기본적인 사용 흐름은 휴대폰 사진첩만큼 간단해야 한다.

# 4. Onboarding & Authentication

## 4.1 최초 실행

1. PrivateVault 로고 표시
2. 개인정보 보호 정책과 복구 불가 안내
3. 기기 보안 기능 지원 여부 확인
4. PIN 또는 패턴 방식 선택
5. 인증 정보 등록
6. 인증 정보 재확인
7. 복구 불가능 경고 확인
8. 로컬 암호화 금고 생성
9. 금고 홈 화면 진입

기기 자체에 안전한 잠금 설정이 없거나 필수 하드웨어 보안 조건을 충족하지 못하면 금고 생성을 차단한다.

## 4.2 숫자 PIN

- 기본 추천: 10~12자리
- 최소 허용: 8자리(보안 검토 전 잠정값)
- 연속 숫자 및 반복 숫자 경고
- 입력값 화면 노출 최소화
- 사용자가 입력한 PIN을 서버, 로그, 분석 시스템 등에 저장하지 않음
- 기기 보안 칩과 별도로 결합하여 암호화 키 보호

PIN만으로 암호화 키를 직접 생성하는 단순 방식은 금지한다.

## 4.3 패턴 잠금

- 숫자 PIN의 대체 인증 방식
- 4×4 패턴 인터페이스 우선 검토
- 충분한 연결점 수 및 패턴 복잡도 요구
- 패턴 궤적 표시 숨김 옵션
- 반복적·단순 패턴 생성 제한
- PIN 대비 추측·관찰 공격에 취약할 수 있음을 안내

패턴의 가능한 조합 수와 실제 하드웨어 보안을 평가한 뒤 고보안 금고에 적합한지 최종 결정한다.

## 4.4 잠금 정책

- 앱 최초 실행 시 반드시 인증
- 앱이 백그라운드로 전환되면 즉시 잠금
- 화면 잠금 또는 앱 종료 시 복호화 세션 종료
- 잘못된 인증을 반복하면 재시도 지연
- 중요 설정 변경 시 기존 인증 재확인
- Face ID 및 생체인증만으로 비밀번호를 우회하는 복구 기능 없음

# 5. Zero-Recovery Policy

**Requirement ID: PV-SEC-001**

비밀번호 분실 후에는 기존 금고의 암호화된 사진·영상·문서에 다시 접근할 수 없어야 한다.

## 절대 금지

- 비밀번호 찾기
- 이메일 복구
- 전화번호 복구
- 복구 질문
- 관리자 마스터키
- 개발자 전용 복호화 기능
- 숨겨진 긴급 접근 경로
- 기기 PIN이나 생체인증만으로 기존 금고 복구

## 비밀번호 분실 처리

1. 사용자가 PIN 또는 패턴을 잊는다.
2. 기존 금고는 계속 잠긴 상태로 유지된다.
3. 기존 암호화 키를 재생성할 수 없다.
4. 사용자는 앱을 삭제하고 재설치할 수 있다.
5. 재설치하면 새로운 독립 금고를 생성한다.
6. 이전 금고의 자료는 복구되지 않는다.

앱을 삭제하면 운영체제에 의해 기존 앱 데이터 자체가 제거될 수 있다. 따라서 이전 데이터가 휴대폰에 영구 보존된다는 의미는 아니다.

## 필수 경고문

**비밀번호를 잊으면 모든 파일을 영구적으로 잃게 됩니다.**

PrivateVault는 비밀번호 복구, 관리자 초기화, 클라우드 백업 기능을 제공하지 않습니다. 앱을 재설치해도 이전 파일은 복원되지 않습니다.

# 6. File Import System

## 6.1 지원 파일

| 종류 | MVP 지원 |
|---|---|
| JPG · JPEG · PNG | 지원 |
| HEIC · HEIF | 기기별 지원 확인 |
| MP4 · MOV | 지원 |
| PDF | 지원 |
| TXT | 지원 |
| DOCX 등 Office 문서 | 내부 렌더링 보안 검증 후 지원 |

지원하지 않는 파일은 가져오기 전에 경고한다.

저장할 수 있지만 금고 내부에서 열람할 수 없는 파일 형식은 기본적으로 허용하지 않는다.

## 6.2 One-Way Import

**Requirement ID: PV-FILE-001**

1. 사용자가 휴대폰의 사진첩 또는 파일 앱에서 파일을 선택한다.
2. 파일 형식과 크기를 확인한다.
3. 저장 가능한 공간을 확인한다.
4. PrivateVault 내부에서 임시 암호화 작업을 수행한다.
5. 암호화된 파일의 무결성을 검증한다.
6. 금고 내부 파일로 등록한다.
7. 사용자에게 원본 삭제를 요청한다.
8. 운영체제에서 허용하면 원본 삭제를 진행한다.
9. 삭제가 불가능한 경우 수동 삭제를 안내한다.
10. 가져오기 결과를 표시한다.

## 6.3 절대 준수 조건

- 암호화 저장이 완료되기 전에 원본 삭제 금지
- 검증 실패 시 원본 삭제 금지
- 암호화되지 않은 영구 임시 파일 생성 금지
- 앱 외부 캐시나 공용 다운로드 폴더에 복사 금지
- 원본 삭제 실패를 성공으로 표시하지 않음
- 기존 클라우드 복사본까지 삭제했다고 주장하지 않음

## 6.4 원본 처리의 현실적 제한

iOS Photos 및 Android 사진·파일 시스템은 각기 다른 접근 권한을 적용한다.

특히 기존 사진첩의 '최근 삭제된 항목', 이미 업로드된 클라우드 사본, 다른 기기에 만들어진 복사본은 PrivateVault가 전부 제거한다고 보장할 수 없다.

사용자가 원본 삭제 결과를 확인할 수 있는 안내가 반드시 필요하다.

# 7. Vault File Management

## 7.1 홈 화면

초기 홈은 네 가지 메뉴를 사용한다.

- Photos
- Videos
- Documents
- Folders

상단에는 금고 잠금 상태와 내부 검색을 배치하고, 하단에는 파일 가져오기 메뉴를 제공한다.

외부 공유 아이콘은 표시하지 않는다.

## 7.2 사진 열람

- 사진 그리드
- 확대 및 축소
- 좌우 넘기기
- 회전 보기
- 전체 화면
- 내부 즐겨찾기
- 파일 삭제

사진의 원본 데이터는 복호화된 파일 형태로 외부 저장소에 생성하지 않고, 보호된 내부 메모리와 렌더링 경로에서 처리하도록 설계한다.

## 7.3 영상 열람

- 내부 영상 플레이어
- 재생 및 일시정지
- 탐색 막대
- 음량 조절
- 전체 화면
- 재생 종료 후 잠금 정책 적용

고화질 영상은 전체 파일을 한꺼번에 복호화하지 않고 청크 단위로 처리한다.

## 7.4 문서 열람

- PDF 페이지 보기
- 확대 및 축소
- 페이지 이동
- 내부 텍스트 렌더링
- 검색 기능은 후속 검토

외부 문서 앱으로 파일을 보내어 열람하는 방법은 허용하지 않는다.

## 7.5 폴더 관리

- 폴더 생성
- 폴더 이름 변경
- 내부 파일 이동
- 내부 폴더 간 정리
- 빈 폴더 삭제

폴더 이름 및 구조도 암호화된 상태로 저장한다.

# 8. Cryptographic Architecture

## 8.1 기술 방향

| 영역 | 권장 기술 |
|---|---|
| 파일 암호화 | AES-256-GCM |
| PIN 기반 키 보호 | Argon2id |
| 보조 키 보호 | 기기 하드웨어 보안 |
| iOS | Secure Enclave · Keychain |
| Android | Keystore · StrongBox/TEE |
| 암호화 난수 | 운영체제 보안 난수 생성기 |
| 데이터 무결성 | 인증 암호화 태그 |
| 암호화 키 저장 | 기기 귀속 보호 저장소 |
| 클라우드 키 저장 | 없음 |

검증된 암호화 라이브러리를 사용하며 자체 암호화 알고리즘을 만들지 않는다.

## 8.2 키 관리 구조

다음은 개념적 설계이며 실제 플랫폼 API 적합성은 PoC로 검증한다.

1. 새로운 금고 생성 시 무작위 마스터키 생성
2. 각각의 파일에 독립적인 데이터 암호화 키 생성
3. 마스터키로 파일별 키를 보호
4. 마스터키는 PIN/패턴 유래 비밀정보와 기기 귀속 보안 키를 모두 필요로 하는 구조로 보호
5. 사용자의 PIN만으로 파일을 직접 복호화할 수 없도록 설계
6. 기기 보안 키만으로도 PIN을 우회할 수 없도록 설계
7. PIN과 하드웨어 보안 요건이 충족될 때만 암호화 키 사용
8. 잠금 시 메모리의 민감정보 노출을 최소화

짧은 인증 정보가 제공하는 엔트로피에는 한계가 있으므로, 단순 해시나 앱 내부 재시도 횟수 제한만으로 보안성을 주장하지 않는다.

## 8.3 파일 암호화

- 파일별 독립 키 사용
- 파일명 및 메타데이터 암호화
- 썸네일 암호화
- 동영상은 안전한 청크 단위 암호화
- 청크별 고유 nonce 및 인증 태그 관리
- 파일 ID·청크 순서·형식을 무결성 검증에 결합
- 암호화가 중단되면 미완성 파일을 금고에 등록하지 않음
- 암호화 오류 시 원본 삭제 금지

## 8.4 플랫폼별 보안

**iOS**

- 기기 귀속 Keychain 설정
- 기기 암호 설정 필수

# 9. Permanent Deletion

## 9.1 삭제 정책

금고 내부 파일을 영구 삭제할 수 있는 사람은 현재 잠금이 해제된 금고의 사용자뿐이다.

삭제된 파일은 복구할 수 없다.

## 9.2 삭제 흐름

1. 사용자가 파일 선택
2. 영구 삭제 선택
3. 삭제 경고 표시
4. 인증 정보 재확인
5. 파일별 암호화 키 파기
6. 관련 메타데이터와 암호문 파일 제거
7. 내부 썸네일 및 인덱스 정리
8. 삭제 완료 표시

## 9.3 대량 삭제

전체 금고 삭제는 별도 메뉴로 제공한다.

- PIN·패턴 재인증
- 영구 삭제 위험 안내
- 명시적 최종 확인
- 금고의 핵심 복호화 키 파기
- 암호화 파일 및 관련 데이터 정리
- 새로운 금고 생성 화면으로 이동

삭제가 실제 저장매체의 모든 물리적 흔적을 제거했다고 주장하지 않는다. 복호화에 필요한 키를 안전하게 폐기하는 것을 우선 보안 목표로 한다.

# 10. Security Monitoring

## 10.1 기본 침입 방어

- 반복적인 PIN 오류 탐지
- 재시도 지연
- 앱 디버깅 및 변조 징후 감지
- 루팅·탈옥 상태의 보안 위험 확인
- 암호화 파일 무결성 오류 감지
- 백그라운드 전환 시 즉시 잠금
- 화면 미리보기 가림
- 민감정보가 로그에 남는 것 차단

## 10.2 대응 정책

| 상황 | 기본 대응 |
|---|---|
| PIN 반복 오류 | 재시도 지연 및 잠금 |
| 앱 변조 의심 | 접근 차단 |
| 루팅·탈옥 탐지 | 금고 사용 제한 |
| 파일 무결성 검사 실패 | 해당 파일 격리·열람 차단 |
| 화면 녹화 탐지 | 표시 가능한 범위에서 화면 가림 |
| 앱 비정상 종료 | 재실행 시 인증 요구 |
| 파일 복사 시도 징후 | 허용되지 않은 기능 차단 및 잠금 |

운영체제 밖에서 이루어지는 파일 복사 시도는 앱이 감지하지 못할 수 있다.

# 11. Self-Destruct Protection

**상태: OWNER 요청사항 반영 / 정확한 자동 발동 조건 미승인**

## 11.1 목표

심각한 보안 침입이 발생했을 때 파일의 복호화 키를 폐기하여 자료 접근을 차단한다.

## 11.2 핵심 방식

Self-Destruct는 물리적 장치 파손이나 위험한 동작을 의미하지 않는다.

금고 암호화 키를 폐기하는 **Cryptographic Erasure** 방식으로 설계한다.

## 11.3 권장 운영

**기본 모드**

- 의심 활동 즉시 잠금
- 접근권한 차단
- 데이터 자동 삭제 없음

**Strict Protection Mode — 후속 검증**

- 사용자가 위험을 이해하고 명시적으로 활성화
- 검증된 심각한 침입 조건에서 키 파기
- 발동 전 공격자가 악용할 수 있는지 분석
- 오탐 발생 시 전체 자료 손실 위험을 명시

## 11.4 금지되는 자동 파기 조건

독립적인 검증 없이 다음 사건만으로 금고를 자동 파괴하지 않는다.

- PIN 1회 오류
- 단순 앱 충돌
- 저장 용량 부족
- 운영체제 업데이트
- 불확실한 루팅·탈옥 탐지 신호
- 앱의 일시적인 보안 검사 실패

자동 자폭 기능은 별도 보안 테스트와 OWNER 승인 후 출시 범위에 포함할 수 있다.

# 12. Privacy & Network Policy

## 12.1 데이터 정책

- 계정 없음
- 서버 사용자 데이터 없음
- 사진·영상·문서 업로드 없음
- 클라우드 백업 없음
- 원격 복원 없음
- 광고 SDK 없음
- 사용자 분석 SDK 없음
- 외부 AI 분석 없음
- 위치 수집 없음
- 연락처 접근 없음

## 12.2 네트워크 정책

PrivateVault의 애플리케이션 기능은 네트워크 연결에 의존하지 않는다.

- Android 앱에는 인터넷 접근 권한을 포함하지 않는 방향
- iOS 앱에는 네트워크 요청을 수행하는 기능 및 불필요한 SDK 미포함
- 릴리스 빌드에서 네트워크 통신 여부 검증
- 비행기 모드에서도 모든 금고 핵심 기능 작동
- 앱 자체적으로 파일 데이터 외부 전송 경로를 제공하지 않음

단, 앱이 통제하지 않는 운영체제·앱스토어의 독립적인 동작까지 금지한다고 주장하지 않는다.

# 16. Security Testing & Acceptance Criteria

## 16.1 필수 테스트

- [ ] 금고에 파일을 넣은 후 평문 원본이 앱 내부 저장소에 존재하지 않는다.
- [ ] 파일명·메타데이터·썸네일에서 민감정보가 노출되지 않는다.
- [ ] 잘못된 PIN으로 암호화 키를 사용할 수 없다.
- [ ] PIN을 잊었을 때 다른 인증 방식으로 우회할 수 없다.
- [ ] 앱 삭제 후 재설치하면 이전 금고가 복원되지 않는다.
- [ ] 개발자용 복구 키가 존재하지 않는다.
- [ ] 인터넷 연결 없이 정상 작동한다.
- [ ] 외부 파일 공유 및 내보내기 경로가 존재하지 않는다.
- [ ] 가져오기 실패 시 원본이 유지된다.
- [ ] 암호화 저장 검증 이후에만 원본 삭제를 요청한다.
- [ ] 원본 삭제 실패를 사용자에게 정확히 알린다.
- [ ] 앱 종료·백그라운드 전환 후 민감 화면이 노출되지 않는다.
- [ ] 지원되는 Android 기기에서 화면 캡처 차단이 작동한다.
- [ ] iOS 화면 캡처 제한의 기술적 한계를 확인하고 사용자에게 과장하지 않는다.
- [ ] 복호화된 영상 임시파일이 외부 경로에 생성되지 않는다.
- [ ] 저장소 부족·강제 종료·전원 차단 상황에서 금고가 손상되지 않는다.
- [ ] 개별 파일 삭제 후 복호화 키가 재사용되지 않는다.
- [ ] 금고 전체 삭제 이후 기존 파일을 복호화할 수 없다.
- [ ] 기기 백업 및 기기 이전에서 암호화 금고의 복원 정책이 준수된다.
- [ ] 루팅·탈옥·디버깅 등 침입 테스트 결과가 문서화된다.
- [ ] 암호화 라이브러리 및 종속성에 대한 보안 검토가 완료된다.

## 16.2 외부 보안 감사

보안 검증 기준으로 OWASP MASVS의 다음 영역을 적용한다.

- Secure Storage
- Cryptography
- Authentication
- Platform Interaction
- Code Quality
- Resilience
- Privacy

독립적인 보안 검토가 완료되지 않은 상태에서는 '해킹 불가능' 또는 '세계 최고 등급' 등의 표현을 사용하지 않는다.

# 18. Business Model

## 기본 원칙

사용자의 파일을 수집하거나 분석하지 않고 수익을 창출한다.

추천 방식은 **앱스토어 유료 다운로드(일회성 구매)** 이다.

### 이유

- 클라우드 서버 운영비 없음
- 광고 SDK 불필요
- 지속적인 서버 구독 의존성 없음
- 보관 파일을 유료 결제로 인질화하지 않음
- 완전 오프라인 제품과 자연스럽게 부합

정확한 가격은 경쟁 앱 가격 조사와 실제 사용성 테스트 후 결정한다.

### 초기 비용 특성

| 항목 | 비용 특성 |
|---|---|
| 파일 보관 서버 | 불필요 |
| 클라우드 저장 | 불필요 |
| AI API | 불필요 |
| 앱스토어 등록 | 플랫폼 정책에 따른 비용 |
| 앱 개발 | iOS·Android 개발비 |
| 보안 테스트 | 핵심 비용 요소 |
| 유지보수 | OS 및 보안 업데이트 대응 |

보안 감사 비용을 절감하기 위해 검증 절차 자체를 생략해서는 안 된다.

# 21. Final Product Vision

**JellyDock PrivateVault**

*Your Files. Your Device. Your Eyes Only.*

PrivateVault는 클라우드 서비스나 파일 공유 서비스가 아니다.

사용자가 자신의 가장 민감한 사진, 동영상과 문서를 오직 본인의 휴대폰 안에 보관할 수 있도록 만드는 고보안 암호화 금고다.

사용자가 금고를 열 수 있는 인증 정보를 잃어버리면 개발자를 포함한 누구도 복구 서비스를 제공하지 않는다.

파일은 금고 안으로 가져올 수 있고, 이후에는 금고 안에서 열람·정리하거나 영구 삭제할 수 있다.

**보안은 편의 기능이 아니라 제품의 최상위 설계 조건이다.**

이 PRD는 디자인 및 기술 검증을 위한 기준 문서이며, 구현과 배포는 OWNER의 별도 승인 후 진행한다.
