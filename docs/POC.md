# Phase 1 Security PoC — 금고 보안 핵심부

`core/` 모듈은 iOS·Android가 공통으로 따르는 금고 보안 로직입니다. 순수 Kotlin(JVM 17 바이트코드)이라 Android 앱에서 그대로 사용하고, iOS는 같은 형식·규칙을 Swift로 옮깁니다.

## 구성
| 파일 | 역할 | 관련 SPEC |
|---|---|---|
| `VaultKeyManager.kt` | 마스터키 생성·잠금 해제, 3회 오류 파기, PIN 변경, 재설치 잔존 키 삭제 | AC-03, AC-04, AC-10, AC-20 |
| `HardwareKey.kt` | 보안칩 키 인터페이스 (Android Keystore/StrongBox, iOS Secure Enclave가 구현) | AC-10, AC-15 |
| `Kdf.kt` | Argon2id(PIN), HKDF-SHA256 | AC-14 |
| `Aead.kt` | AES-256-GCM | AC-11 |
| `ChunkedCipher.kt` | 동영상용 조각 단위 암호화·임의 위치 복호화 | AC-35, AC-44~46 |
| `Vault.kt` | 가져오기(암호화→검증→등록), 목록, 열람, 영구 삭제, 전체 파기 | AC-12, AC-30~32, AC-42, AC-43 |
| `PinPolicy.kt` | PIN 4자리 이상, 흔한·단순 PIN 거부, 강도 | AC-01, AC-03a, AC-06 |
| `AttemptCounter.kt` | 실패 횟수: PIN 검사 *전에* 디스크에 기록 | AC-03 |

## 키 구조
```
A   = Argon2id(PIN, salt, 256 MiB / 3회 기본값)
H   = HardwareKey.mix(A)          ← 보안칩 안에서만 계산
KEK = HKDF-SHA256(A || H, salt)
envelope = AES-256-GCM(KEK, 마스터키, AAD = 헤더[파라미터·salt])
파일키 = 파일마다 무작위, 마스터키로 감싸서 저장
```
- PIN만으로도, 보안칩 키만으로도 열 수 없습니다. 복구 키는 없습니다.
- 헤더(Argon2 비용값 포함)는 인증 데이터라 바꾸면 열리지 않습니다.

## 설계 결정 (SPEC과 다른 점·보완)
1. **PIN 자릿수를 저장하지 않음:** 자릿수를 저장하면 공격자에게 길이가 노출됩니다. 그래서 "자릿수 미만 입력 미계산(AC-06)"은 최소 4자리 미만 입력을 계산하지 않는 방식으로 구현했습니다. 잠금 화면 점 표시는 입력한 만큼만 보여야 합니다(디자인 반영 필요).
2. **카운터 파일이 없거나 손상되면 1회만 허용:** 새 시도 3회를 주지도 않고, 그것만으로 금고를 파기하지도 않습니다(PRD 14장 "오류로 임의 삭제 금지").
3. **3회 파기 시 암호문도 정리:** 키 파기 후 남은 암호문은 읽을 수 없으므로 함께 지웁니다.
4. **검사 도중 앱 오류(메모리 부족·보안칩 오류)는 시도 횟수에서 되돌림:** 결과를 알 수 없었으므로 공격자에게 이득이 없습니다. 반대로 **앱이 강제 종료**되면 기록은 남습니다. 세 번째 시도 중 강제 종료되면 다음 실행 때 금고를 파기합니다(종료로 마지막 기회를 무한 반복하는 공격 차단). 그래서 앱은 PIN 검사 전 남은 메모리를 확인해야 합니다(실기기 단계 과제).
5. **키 일부만 없을 때(보안칩 키 일시 조회 실패 등)는 파기하지 않음:** `KeysUnavailableException`으로 알리고 사진은 지우지 않습니다. 사진 삭제는 실제 3회 오답 파기 때만 일어납니다.
6. **원본 삭제 허용 조건:** 앱이 원본을 따로 한 번 더 읽어 계산한 SHA-256을 넘겨주고, 금고 사본과 일치할 때만 `safeToDeleteOriginal = true`입니다. 원본 스트림이 중간에 끊겨도(클라우드 사진 미다운로드 등) 원본을 지우지 않습니다.
7. **동시 입력 차단:** 여러 스레드·프로세스가 동시에 PIN을 넣어도 검사는 한 번에 하나씩만 됩니다(파일 잠금). 12개를 동시에 넣어도 검사는 정확히 3번입니다.
8. **전원 차단 대비:** 파일 쓰기 후 파일과 폴더 기록을 모두 저장 장치에 강제 기록(fsync)합니다. 재부팅 후 카운터가 예전 값으로 돌아가거나 가져온 사진이 사라지지 않게 합니다.

## 검증 결과 (이 환경, JVM)
- `gradle build`: 컴파일(경고=오류), ktlint, 테스트 57개 통과
- 테스트 범위: 정상/오답 PIN, 3회 파기 후 정답 PIN 거부, 파기 후 envelope 복원 공격, 검사 중 강제 종료, 세 번째 시도 중 강제 종료, 보안칩 오류 시 미계산·미파기, 12개 동시 입력, 두 개 관리자 객체 공유 카운트, 다른 기기 키로 열기 실패, 헤더 변조(거대 메모리 값 포함), 카운터 범위 밖 값, 숫자 아닌 입력, PIN 변경 중 3회 오답, 조각 잘라내기·순서 바꾸기·비트 변조(순차·임의 위치), 디스크에 평문·메타데이터 없음, 실패·잘린 가져오기 시 등록 없음, 원본 해시 없으면 삭제 불허, 가져오기 중 잠금, 기존 금고 위 재생성 거부, 삭제 후 암호문 복원해도 못 읽음, 반쯤 지운 항목 정리, 파기 도중 강제 종료 후 재실행 시 파기 완료, 남은 임시 파일 삭제, 경로 조작 차단

## 내부 QA 리뷰
- 1차 리뷰: HIGH 3건, MED 4건, LOW 다수 발견 → 모두 수정 (CHANGELOG 참고)
- 2차 리뷰: 1차 결함 8건 모두 수정 확인. 새 MED 1건(파기 도중 강제 종료 시 금고가 영원히 막힘) + LOW 3건 발견 → MED와 LOW 2건 수정
- 3차 확인: 2차 수정분 정상 확인. 새로 넣은 임시 파일 정리가 잠금 밖에서 돌아 envelope를 망가뜨릴 수 있는 MED 1건 발견 → 금고 잠금 안으로 옮겨 수정
- 알려진 한계(미수정, 기록):
  - 검사 오류 후 시도 횟수 되돌리기 쓰기마저 실패하면(디스크 오류 2회 연속) 그 시도는 계산된 채로 남습니다.
  - PIN 변경은 마스터키를 그대로 두고 다시 감쌉니다. 루팅 + 포렌식으로 플래시에 남은 옛 envelope를 복구하면 이 기기에서 옛 PIN으로 열릴 수 있습니다. 마스터키 교체(모든 파일키 재포장)는 MVP 단계 과제로 남깁니다.
